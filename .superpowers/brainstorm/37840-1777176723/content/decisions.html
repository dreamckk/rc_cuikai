关键工程决策与取舍

对应作业要求的三个核心问题

1. 系统边界

✅ 在系统内解决
  • 接收业务系统的通知请求
  • 异步可靠投递（at-least-once）
  • 自动重试 + 指数退避
  • 死信队列兜底 + 告警
  • 投递日志记录（审计）
  • 手动重试运维接口
  • 多供应商配置管理
❌ 明确不解决
  • 幂等性：外部系统需自己保证（我们 at-least-once，可能重复投递）
  • 请求鉴权：调用方身份认证留给 API 网关层
  • 消息顺序：不保证同一供应商消息有序
  • 回调通知：不处理外部 API 的异步回调
  • 速率限制：不做 per-supplier 限流（MVP 阶段）

2. 可靠性与失败处理

投递语义

At-least-once：宁可重复投递，不可丢失。原因：外部系统（广告/CRM/库存）通常能设计幂等接口，而丢通知的业务损失更难接受。

外部系统长期不可用

分三阶段处理：

  1. RocketMQ 自动重试 16 次（跨越约 4 小时）
  2. 超限后进入 DLQ，触发监控告警
  3. 人工介入：等供应商恢复后，通过运维接口批量重发 DLQ 消息

3. 取舍与演进

AI 建议中我没有采纳的
  • 事务消息（本地消息表）：AI 建议用 RocketMQ 事务消息彻底解决网关写入 MQ 失败的问题。我认为对 MVP 过度设计——网关写入失败的概率极低，且业务系统可以重试调用网关，不值得引入额外复杂度。
  • per-supplier 限流：AI 建议对每个供应商做调用频率限制。MVP 阶段通知量可控，过早优化。
  • 多 Topic 按供应商隔离：AI 建议每个供应商一个 Topic。增加运维复杂度，单 Topic + 并发消费足够。
未来演进路径
  • 流量增长：Dispatcher Worker 水平扩展，增加 RocketMQ 消费者并发数
  • 供应商增多：引入 per-supplier 限流 + 隔离 Topic，防止一个慢供应商阻塞其他
  • 可靠性要求提升：引入本地消息表 + 事务消息，彻底消除网关单点故障
  • 可观测性：接入 Prometheus + Grafana，监控投递成功率、延迟、DLQ 积压
