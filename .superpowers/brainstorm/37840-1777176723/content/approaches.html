三种架构方案

选择最适合你的通知投递系统架构

A

方案 A：同步网关 + RocketMQ 异步投递（推荐）

流程：业务系统 → HTTP POST → 网关服务（写入 RocketMQ）→ Worker 消费 → 调用外部 API

核心思路：网关只负责接收和入队，Worker 负责投递和重试。两层职责清晰分离，网关响应极快（<10ms），Worker 失败自动触发 RocketMQ 内置重试 + DLQ。

优点

  • 接收与投递完全解耦
  • RocketMQ 原生延迟重试（1s/5s/30s/...）
  • DLQ 兜底，不丢消息
  • 业务系统无需等待外部 API 响应

缺点

  • 需要运维 RocketMQ
  • 链路更长，排查需要跨服务
B

方案 B：DB 任务表 + 定时轮询

流程：业务系统 → HTTP POST → 写入 DB 任务表 → 定时任务轮询 → 调用外部 API → 更新状态

核心思路：用数据库替代 MQ，省去中间件依赖。定时任务（如每 30s）扫描 pending 任务并投递，失败后更新重试次数和下次执行时间。

优点

  • 无额外中间件，基础设施简单
  • DB 事务保证写入原子性
  • 任务状态可直接查 DB，排查简单

缺点

  • 高并发下 DB 轮询有性能瓶颈
  • 延迟较高（轮询间隔级别）
  • 需要自己实现退避重试逻辑
C

方案 C：RocketMQ + 本地消息表（事务消息）

流程：业务系统 → HTTP POST → 本地消息表（DB 事务写入）→ 事务消息发送 RocketMQ → Worker 消费 → 调用外部 API

核心思路：在方案 A 基础上，用 RocketMQ 事务消息保证"写 DB 和发 MQ"的原子性，彻底解决网关写入 MQ 失败导致丢消息的问题。

优点

  • 最强可靠性保证
  • 网关宕机不丢消息（事务回查机制）
  • 完整的本地消息记录

缺点

  • 实现复杂度最高
  • 需要同时维护 DB + MQ
  • 对 MVP 来说过度设计

💡 我的推荐是 方案 A：对 MVP 而言，RocketMQ 的内置重试 + DLQ 已经足够可靠，架构清晰，工程判断务实。方案 C 的事务消息适合未来演进。
